# Architecture

Reversed engineering Icsee is a Swift 6 app using SwiftUI for views and AppKit for native windows. It builds directly with `swiftc`; no package resolver or Xcode project is needed.

```mermaid
flowchart LR
    Board[Camera grid / cinema] --> Session[Shared CameraSession]
    Popup[Floating / fullscreen window] --> Session
    Store[CameraStore] --> Board
    Store --> Popup
    Keychain[macOS Keychain] --> Credentials[Credential sheet]
    Credentials --> Session
    Session -->|authenticated playlist through stdin| FFmpeg[External FFmpeg process]
    FFmpeg -->|RTSP over TCP| Camera[Camera on LAN / VPN]
    Camera -->|video| FFmpeg
    FFmpeg -->|MJPEG stdout| Parser[JPEGFramer]
    Parser --> Session
    FFmpeg -->|stderr in memory| Diagnostics[Bounded diagnostic classifier]
    Diagnostics --> Session
```

## Lifecycle

`CameraStore` owns one session per saved camera. Grid, cinema, popup and menu bar preview observe the same session. Changing a name preserves it; changing an endpoint stops the old stream. Closing a popup releases that view only. Removing a camera stops its session and removes its saved credentials. Closing the last viewer leaves the menu bar running and suspends live decoding; authenticated connection intent stays in memory until explicit Stop, failure or Quit. Each native video view registers demand only while its window is visible and unoccluded. The highest visible render profile wins, so opening a preview never downgrades a visible main or floating view. Application termination removes the status item and event monitor, closes auxiliary windows and stops all sessions.

Each stream has a generation identifier so completion or frames from an old decoder cannot update a replacement connection. Initial connection times out after 20 seconds without a frame; an established stream times out after 12 seconds without a new frame. A 401 before any frame triggers at most one retry using a Sofia-derived query credential. Errors after successful video do not silently enter a retry loop.

FFmpeg requests VideoToolbox hardware decoding, with one software fallback if hardware setup fails before a frame arrives. Decoder, filter and encoder threads are bounded. Cinema/floating/fullscreen views use the existing 1280-pixel-width / 15 FPS cap; grid cards use 800 pixels / 5 FPS; preview alone drops frames before scaling/JPEG encoding to 480 pixels / 5 FPS. Audio is discarded. MJPEG frames cross stdout and Swift displays `NSImage` instances. Only image changes invalidate the video view; repeated live-state/frame-count assignments do not invalidate the surrounding board. Hidden demand cancels the watchdog, closes the decoder and drops the frame. Native occlusion, minimize, close, application hide and sleep notifications drive updates without polling. Active video still has CPU, GPU and memory costs; see [performance measurements](PERFORMANCE.md).

## Build and test decisions

`build.py` compiles arm64 for a macOS 14 minimum and verifies the app's signature. The app bundle and display name are `Reversed engineering Icsee`; its executable is `ReversedEngineeringIcsee`. The legacy bundle identifier `local.CamMac` and Keychain service `local.CamMac.camera` intentionally stay stable to preserve preferences and saved credentials across the rename.

The original icon is generated by `Tools/GenerateIcon.swift`; checked-in PNG and ICNS assets are used by the README and every app build. `CFBundleIconFile` points to the copied ICNS resource. `version.json` supplies release version/build numbers.

`Tools/build_ffmpeg.py` verifies a pinned official source archive and builds a standalone LGPL arm64 decoder targeting macOS 14, with no Homebrew library dependencies. `build.py --bundle-ffmpeg` places the separately signed decoder in `Contents/MacOS/ffmpeg`, where the existing auxiliary-executable lookup finds it first. Licenses, source location and configuration are signed resources. The quick development build omits the decoder and uses an installed copy.

`Tools/package_release.py` builds a fresh bundle, creates DMG/ZIP files and verifies the app from both distributed formats. `Tools/verify_bundle.py` checks native icon/signatures, architecture, deployment target, system-only dynamic dependencies and notices; it decodes synthetic H.264/HEVC frames with a system-only PATH. See [release procedure](RELEASING.md).

Localization uses standard `en.lproj` and `pt-BR.lproj` bundles. English is the development language; macOS selects the best supported preferred language and honors its per-app language setting. SwiftUI literals use native localization; runtime/error/conditional strings use `String(localized:)`. `InfoPlist.strings` localizes the OS network-permission description. Language selection does not rewrite camera profiles, names, credentials or RTSP data. Restarting the app applies preference changes.

Direct `swiftc` builds avoided an incompatible Swift Package Manager `PackageDescription` module in the original local toolchain. `ViewState` explicitly names `SwiftUI.State` to avoid an SDK macro name collision in that environment. Neither workaround is a runtime dependency.

`test.py --core-only` runs deterministic parser/protocol checks and a fixture app bundle in separate processes with volatile `AppleLanguages` arguments. Cases cover English, `en-BR`, `pt-BR`, `pt-PT`, an unsupported language and ordered preferences; catalogs and interpolation types are checked too. User system preferences are never changed. Default tests additionally check native popup ownership, reuse, reopening, empty first launch and saved-profile restoration. `--interactive` also checks real frames from a loopback-only synthetic RTSP peer, preview/window render demand, suspend/resume, menu selection, rendered English/Portuguese SwiftUI, native fullscreen and Escape; it needs an active desktop. None of these tests opens a real camera connection.

## Menu bar lifecycle

An app-owned `CameraAppLifecycle` installs one `NSStatusItem` and `NSPopover` after the main SwiftUI scene appears. Native tracking opens the preview after a short hover and allows pointer handoff into the panel. Clicks pin the preview while selecting a camera. The panel contains only the selector and video. Hover never touches Keychain. Opening a visible preview resumes its previously authenticated session if needed; a never-connected or explicitly stopped camera stays disconnected. The chosen camera UUID is a separate preferences key; camera profile encoding and credential service identifiers stay unchanged.

The popover observes the same store and session as the other views. The Dock reopen delegate routes to the production main-window `OpenWindowAction` to reopen the closed scene. Explicit Quit removes tracking/monitor resources and cancels pending hover work before stopping sessions. Interactive fixtures cover native popover behavior and closing/reopening the actual SwiftUI scene without camera connections.

## Camera control connections

Native control windows share the existing video session but own independent ONVIF and DVRIP clients. `ONVIFClient` handles bounded SOAP/XML, authentication, profiles/options, movement/presets and imaging writes. `DVRIPClient` handles framed TCP sessions, serialized configuration transactions and keepalive. `DeviceJSON` preserves structured values and applies edited leaves to fresh values with conflict checks.

`CameraControlModel` owns per-camera tasks and generation guards, capability/error state, drafts, discovery and movement cleanup. `CameraControlsView` and `DeviceSettingsEditor` provide native controls without automatic writes. `CameraWindows` retains closed-window cleanup tasks; `CameraAppLifecycle` delays normal termination until movement/restart cleanup completes. See [control guide](CAMERA_CONTROLS.md) for limits and validation.

## SD-card recording sessions

`DVRIPRecordingClient` owns separate authenticated query/download transports, typed camera wall-clock values and bounded history/calendar/storage operations. Its media framer preserves download flags without loosening the settings client's JSON rules. `RecordingMediaParser` and `RecordingMovieWriter` turn completed raw XM streams into timestamped native movies, validate actual decoding and retain explicit source/movie mappings and audio/timing disclosures.

`CameraRecordingsModel` owns the player, queries, transfer/conversion/export tasks and one private temporary directory. Generation guards prevent retired operations from replacing a new selection. `CameraRecordingsView` provides calendar/list/timeline, native AVPlayerView and explicit exports. `CameraWindows` tracks its shutdown together with existing control cleanup; live `CameraSession` remains independent. See [recordings guide](RECORDINGS.md).
